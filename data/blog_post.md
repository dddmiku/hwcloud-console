# 使用 Go 与 Playwright 实现浏览器自动化的一次实践

最近在做一个浏览器自动化的练习项目，用 Go 调用 Playwright 完成登录态复用、页面元素定位与表单提交。这里记录几个踩过的坑和最终的实现思路，供同样在写自动化脚本的同学参考。

## 为什么选 Go + Playwright

Node 生态里 Playwright 是一等公民，但业务侧的服务大多用 Go 写。playwright-go 提供了完整的能力：持久化上下文、cookie 注入、选择器等待、文件上传、剪贴板操作。把它嵌进 Go 程序，就能在同一个进程里既做 HTTP 请求也做浏览器操作。

## 登录态的两种保存方式

第一种是 cookie 文件。登录成功后把上下文里的 cookie 导出成 JSON，后续启动新上下文时再 AddCookies 回去。这种方式轻量，适合纯 HTTP 接口调用。

第二种是持久化 profile。LaunchPersistentContext 指定一个目录，浏览器会把 localStorage、IndexedDB、cookie 全部写进去，下次直接复用。缺点是目录会越来越大，且不能同时被两个进程打开。

实践中我是两种混用：HTTP 接口走 cookie 文件，需要操作复杂页面时走持久化 profile。

## 元素定位的稳定性

自动化的脆弱点几乎都在选择器上。我的经验是优先用语义定位：

- `GetByRole` / `GetByLabel` 这类无障碍选择器最稳，站点改版时不容易失效
- 文本定位要加 `Exact: true`，否则 "确定" 会匹配到 "取消并确定"
- 实在没有语义特征时再退回 CSS 选择器，并且写成集中管理的常量

另外所有点击都应该包一层"等待可见"，页面是 SPA 的时候元素存在但不可见非常常见，直接 Click 会超时。

## 超时与重试

Playwright 默认超时 30 秒，对于需要等待后端渲染的页面偏短。我的做法是把超时分级：普通元素 15 秒，需要等网络请求的 45 秒，登录跳转这类 5 分钟。

重试不要写成无限循环。固定次数（比如 2 次）配合递增的等待，失败后抛出明确错误，比静默重试更容易排查。

## 小结

自动化脚本的价值在于稳定复现。把选择器集中管理、把超时分级、把错误信息写清楚，这三点做到之后，维护成本会下降一个数量级。
